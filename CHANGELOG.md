# Changelog

What changed in each release, in four fixed parts. How it is kept: [docs/RELEASING.md](docs/RELEASING.md).

## Unreleased

### Changes results

- `eds`: a negative element value (INCA can report e.g. Ru −0.1 wt% after background subtraction) now counts as 0 in the metal basis instead of inflating the other metals when renormalised to 100. The element stays with 0 (`metal_basis.taken_as_zero` lists it; the bar chart and summary show it as n.d.), the table as recorded is unchanged, and a new review check `negative_value` asks you to look at the spectrum. The `low_concentration` check now also lists its elements (`elements`), which the report's tables use. Reports without negative values give the same numbers, but are marked out of date.

### Settings migrated

### New

- Safer guard (no results change): in unattended and postdoc runs the read-only commands (`cat head tail sed ls wc grep rg nl`) are allowed only in strict forms (`sed -n 'N,Mp'`, `rg -n PATTERN PATH`, ...; the refusal message lists them), with every path inside the project and no `$` or `~user`: `sed -n 'w f'`, `rg --pre cmd`, `cat $HOME/...` are refused. The hook launcher no longer lets everything through when it cannot find labpipe: `labpipe project sync` writes `.labpipe/python`, and in a project with `config/local.yaml` an unfound or failing guard blocks the call and names the fix. docs/SAFETY.md.
- The report reads down columns: the EDS overview has one row per measurement and one column per element (metals, then non-metals, by atomic number) in two tables (metals at%, all elements wt%) with faint bars, n.d./grey/– marks and a grey nominal row; the XRD overview has a ± σ in its own cell, the closest reference and Δa; the cards' key results are small tables. A slim sticky navigation bar, sticky table headers, folding samples (fold all), captions under every figure (also the alt text) and a print style (one card per page). New setting `report.sample_order: name | samples | property:<name>` orders the samples everywhere in the report and in `labpipe dataset`.
- Comparison figures across samples: the report's new section "Compare samples" (`report.sections` has `compare`, and `report.compare` chooses figures by name, e.g. `{xrd: [lattice-fcc], eds: false}`) draws a dot plot per quantity (one dark filled marker per measurement, samples in the report's order, a σ bar where the analysis gives one, an optional nominal as a grey diamond) and the figures a method makes itself, into `analysis/_compare/<method>/<name>/` (`plot.png`, `plot.pdf` for papers, `figure.html` for the report, `provenance.json` with the figure's spec and the hash of every output, which `labpipe replay` redraws from). In the report each figure is interactive (plain JavaScript, offline): a checkbox per measurement, All/None, and a row of sample buttons that switches a sample off in every figure; nothing is saved. `labpipe compare [--method M]` draws them alone, and a figure is redrawn only when something it depends on changed. The plot style has a `compare:` block (`plots.compare`). The navigation bar is a little larger and its scroll bar thicker, grouped (sections, methods, samples) and highlights the part you are reading.
- Methods can have their own comparison figures: `compare: <module>` in methods.yaml (also in a lab method's `lab/methods.yaml`), a module with `figures(measurements, context)` returning specs of the figure kinds `dots`, `lines` (stacked patterns, overlaid or normalised in the report), `bars` and `images` (`labpipe.comparekinds`), and optionally `COVERS` (quantities its figures replace, so the default `all` does not draw them twice). A failing hook is listed as "not drawn" with its reason. docs/ADDING_A_METHOD.md.
- `xrd` comparison figures (no results change): the measured patterns stacked on one 2θ axis (read from the raw files, checked by sha256, thinned to at most 2000 points keeping every peak) with the candidate references' predicted lines as ticks, and the lattice parameter a per sample with the candidate references' a as vertical lines (`patterns`, `lattice-fcc`; the latter replaces the generic `xrd.a.*` dot plot by default). Crystallite size stays a generic dot plot. docs/methods/xrd.md.
- The analysts and the postdoc word their claims by `docs/WRITING.md` (adapted from K-Dense's scientific-writing skill): observation apart from interpretation, the verb matching the evidence, no cause from a trend, zero vs missing vs below detection, concrete limitations, the alternative named.
- Comparison figures for EDS and SEM: `eds` draws the composition bars (one 100 % bar per measurement, fixed colour per element, the nominal as a grey bar under it; replaces the `eds.at.*` dot plots, which now show the nominal when asked for) and `sem` the grid of images by gallery magnification, in "Compare samples". No analysis or plot result changes.
- Your own analyses in the report (no results change): figures, tables and notes you made elsewhere (an Origin fit exported as PNG and CSV) go into the data folder, and `labpipe methods import NAME --folder F --files "*.png,*.csv,*.md" --description D` (or: tell your agent "include my Raman fits from Raman/fits") takes them in, as a kind of analysis of your project with its own analyst agent. Files with the same name before the extension are one measurement (the sample from the file name, or `--sample-from folder`). labpipe copies and hashes them (tables as text, exactly as written), checks what a reader needs (units in the header, a description, a table for a figure) and shows them on a card marked "your analysis, made outside labpipe"; named `quantities` from a table column reach `labpipe dataset` and the comparison figures. It never redoes your analysis, and `labpipe replay` checks the files instead of redrawing them. Excel is not read yet (export CSV). The unrecognised-files messages name the command. docs/methods/imported.md.
- `uninstall.sh` (Linux, macOS): lists what it removes (labpipe's containers, volumes, images, the stored login, the pop-up unit, the installation, the link, your defaults; `--keep-config`), asks once, `--dry-run` only shows. Projects and data are never touched; `podman-restart.service` (shared by all your Podman containers) and a read-only view are only named. The README is shorter (what you need first; the agent does the rest); the full native install moved to `docs/NATIVE.md`, the project folder layout to `docs/settings/project.md`.

- Data and project never overlap: `project new` refuses a data folder inside the project (as it refused the project inside the data), `labpipe doctor` reports an overlap as an error, and `container start` / `setup` refuse with the reason (the container mounts the project writable, so data inside it would have been writable). No results change.

- Review flags of code-only methods reach you: the SEM gallery lists them under "Check before using" (image, check code, message) and marks the image, the overview row counts "N to check", the watcher notifies once per measurement ("N SEM measurement(s) to check", also in `logs/review_queue.md`); the same for the lab's own methods without an analyst. No results change.
- Edited lab method code is never run stale: the watcher analyses code-only methods one fresh process per measurement (a process that dies is recorded as failed with its error output) and restarts when `lab/methods/` or `lab/methods.yaml` changes. No results change.
- A file moved or renamed in the data folder takes its output folder along and is analysed again there; `labpipe doctor` warns while an output folder still holds the analysis of two files (`shared_output_dirs`). Fixed: a moved file used to be taken for a duplicate of its own old place, so it was never analysed again and dropped out of the report.
- Every input of a measurement is tracked: a method can name its companion files in `methods.yaml` (`companions: module:function`; also in a lab method), the scanner records their hashes with the main file's, and a done or stale measurement goes back to pending when one changes, appears or disappears ("companion S-1 a001.txt changed"). SEM tracks its JEOL `.txt`, EDS the images its report links. No results change. docs/ADDING_A_METHOD.md.

### Needs your action

- SEM and EDS measurements analysed before companions were tracked are compared with the companions recorded in their `provenance.json` at the first `labpipe scan`. Where they agree nothing happens. Only a measurement whose `.txt` or linked image really differs from what it was analysed with goes back to pending ("companion <name> changed") and is analysed again; one with no companions recorded adopts the current files.
- Two raw files with the same name in different folders (`XRD/S-1_scan.xrdml` and `XRD/old/S-1_scan.xrdml`) used to share one output folder, and the second analysis moved the first one's outputs aside. Each measurement now has its own folder, chosen at its first analysis and kept in the manifest: `<measurement_id>`, or `<measurement_id>~<6 characters of the entry id>` when another file already holds that name. labpipe refuses to write into a folder whose `provenance.json` names another file (the analysis fails with the reason). In an existing project `labpipe scan` finds measurements that share a folder: the one whose provenance is in the folder keeps it, the others go back to pending ("shared an output folder with <path>; analysed again into its own folder") and are analysed again into their own folder; nothing is deleted. A moved raw file (a new path) is a new measurement and also gets its own folder once. No analysis result changes.

## v0.2.0 — 2026-10-20

### New

- Code and projects are separate. The code folder (`~/.local/share/labpipe/app`) is replaced by updates; a project is your own folder (`labpipe.yaml`, `config/`, `context/`, `lab/`, results) that updates never write to. `labpipe project new` creates one, `labpipe project sync` regenerates its generated files.
- One-command installer (`install.sh`, `install.ps1`) and a slim host install (Python 3.10+, PyYAML only). The analysis runs in a container, one per project (Podman or Docker); `labpipe setup --first` asks the first questions: tools, models, login, first project. The installer installs the newest release; `--main` installs the development state.
- `labpipe --version` shows the version and the release tag.
- The postdoc: an overall analysis of the whole dataset on request (`labpipe postdoc`), with a `context/` folder for aims and documents, named quantities per sample (`labpipe dataset`, compare differences and trends), and its own section in the report.
- Settings pages (`docs/settings/`) and your own preferences file `lab.yaml`; plot and report settings with layouts, grouping, sections, filters and extra reports; `labpipe replot` redraws figures after a plot setting changed.
- Every method has its own analysis version and plot version (`labpipe methods versions`): only a change in the calculation marks analyses stale; a plot change only marks the plot out of date.
- The lab's own methods and references live in the project (`lab/methods.yaml`, `lab/methods/<name>/`, `lab/references/xrd`); updates never touch them. `labpipe methods new` scaffolds into `lab/`, `labpipe methods check` runs in the container.
- `labpipe update` goes from release to release, and back (`--to`): it shows the changelog first, can preview what the release would change in your own numbers (`--preview`, by code, nothing is changed), backs up your settings (`backups/<release>/`), switches the code, migrates renamed settings (diff shown, asked), regenerates the generated files, restarts the container and lists the analyses that are out of date (nothing is redone by itself). Settings migrations (`labpipe migrate`; old names keep working for one release) and versioned note checks (notes that passed stay valid when the rules get stricter) come with it. [docs/settings/updates.md](docs/settings/updates.md)
- First conversation: after setup the agent shows you around with your own data (`docs/ONBOARDING.md`: your files, each method's setup questions, a first result explained, a short tour; any step can be skipped, "tour" repeats it). `labpipe onboarding` keeps the record; `labpipe doctor` shows `onboarding` as a warning while steps remain.
- `labpipe doctor` says when a project was set up with another release than the installed one (`project_release`).
- `labpipe replay` needs the same analysis and plot version, not the same commit.
- Every method page has a "Reading the plot" section (what each line, panel and colour is, good versus look again, which plot settings change it), and so does the template for your own methods (`labpipe methods check` warns while it is missing). The report starts with a collapsed "How to read this report" box, generated from the report settings (`how_to_read: false` hides it).
- The container starts by itself when you log in. The installer asks ("Start the container by itself when you log in?", default yes) and `labpipe automation setup` sets it up: Podman on Linux enables the user unit `podman-restart.service` (after your yes; starting without logging in needs `loginctl enable-linger $USER`, which is shown and never run), Docker restarts the container when Docker starts, Podman on macOS/Windows needs the podman machine to start at login (untested). `labpipe doctor` has an `autostart` item.
- Automatic processing runs only in the container. The native systemd watcher and nightly timer, and the native macOS/Windows pop-ups, are removed; `labpipe automation watch` refuses outside the container. `labpipe automation run` (one pass by hand) and the notifications page stay; Linux pop-ups go through `labpipe container popups on`.
- XRD quantities use a generic fcc name in every sample, with the closest reference as "possibly X"; no AI cost limit unless you set one.

### Needs your action

- Old native automation: if you set it up with an earlier version, remove its units: `labpipe automation setup` (shows them and asks first), or `systemctl --user disable --now labpipe-watch.service labpipe-nightly.service labpipe-nightly.timer`, then `rm ~/.config/systemd/user/labpipe-watch.service ~/.config/systemd/user/labpipe-nightly.service ~/.config/systemd/user/labpipe-nightly.timer` and `systemctl --user daemon-reload` (`labpipe doctor` warns as `old_automation` until then). Then run `labpipe automation setup` once to start the container at login.
- Existing clones and test setups: reinstall with the new installer and create a project with `labpipe project new <folder> --data <data folder>`. There is no adopt of an old layout.
