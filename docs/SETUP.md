# Setting labpipe up with the user (for agents)

Read this when `labpipe doctor` says `ready: false`. Lead the user **one item at a time**: take `next` from the doctor output, explain in two or three plain sentences what it is and why it matters, do it together, rerun `labpipe doctor`, repeat.

- **Project**: doctor's first item says which project this is (or that there is none: `labpipe project new <folder>`, which the user runs; suggest `~/labpipe-projects/<name>`, never a synced folder). "Generated files out of date" means `labpipe project sync`. The lab's own conventions go in `lab/LAB.md` (ask the user, then write it). If the user is unsure what lives where, explain the three folders (README → Three folders): the **code** (labpipe itself, replaced by updates), their **data** (only read), and the **project** (their settings, context, additions and every result; where they open the agent tool).
- **Install** (first thing, if `labpipe` is missing or `doctor` says there is no project): the one-line install in README → Install asks the agent tool, models, login, the first project and starts the container (`labpipe setup --first`). The user runs it. If it stopped at a missing Podman or agent tool, it showed the commands; the user runs them and reruns the installer. Defaults for new projects are in `~/.config/labpipe/defaults.yaml`.
- **`project_release`** (a warning, never blocking): this project was set up with another release than the installed one. Show `labpipe update --check`; the user runs `labpipe update` in their terminal, never you. `docs/settings/updates.md`.
- **`settings_migrations`** (a warning, never blocking): an update renamed settings the user still has under their old names. Show `labpipe migrate` and its diff; apply (`labpipe migrate --apply`, backup included) only with their OK. `docs/settings/migrations.md`.
- **Optional packages**: a command that needs one (e.g. pymatgen for `labpipe xrd refs build`) prints the exact install command for this installation. Show it, explain what it is for, and let the user run it; never run it yourself.
- **`labpipe setup`** (native mode, without a container) is the guided alternative for the raw-data folder, the sandbox check, models per role and a pointer to container mode for automation (the installers offer it). It asks questions, so the user runs it in their own terminal; suggest it. Single steps: `labpipe setup --only raw-data|files|sandbox|agents|automation`. If the user prefers to do it with you, follow the items below.
- **Raw data location** (`config/local.yaml`): ask where the instrument files are and how they get there (copied by hand, exported from the instrument PC, a network drive, a sync client; none is required). In container mode the data folder is mounted read-only and nothing more is needed. Native mode only: explain the two folders in plain words: their **data folder**, where they put files, and the **read-only view** labpipe reads from (docs/NATIVE.md → The read-only view). The two ways to get a read-only folder are in `docs/SAFETY.md`. Get the exact commands with `labpipe readonly-view --source <their raw folder>` (it prints them for their OS, paths filled in); the user runs them. Record the data folder as `source:` of the raw root and list it under `protected_paths`. Editing `local.yaml` always asks the user for approval; that is intended.
- **Recognising the user's files**: right after the data folder is set (AGENTS.md → Recognising the user's files).
- **Sample IDs**: doctor shows file names that give no sample ID. Show them, ask the user how their files are named, then adapt `config/pipeline.yaml` → `sample_id.pattern` (or add overrides in `config/sample_ids.yaml`). Rerun doctor until the examples look right to the user.
- **Method specifics**: for each method the user has data for, the setup questions in `docs/methods/<method>.md` → Setup (e.g. XRD reference phases and internal standards). Put the answers into settings, never code.
- **First analysis**: `labpipe scan`, pick one file with the user, `labpipe <method> analyze --entry ID`, show `plot.png`, walk through `results.json` and its checks, write the notes (delegate to the method's analyst). Then explain steering (AGENTS.md) with their own plot.
- **Agents and models**:
  - Ask which agent tool the user works with (Claude Code, Codex, OpenCode).
  - Ask which model each role should use; `labpipe setup --only agents` asks the same in the terminal. Explain each role in a sentence:
    - **supervisor**: runs the commands and keeps the books, on every new measurement. A small, fast model is enough.
    - **analysts**: look at one measurement's plot and write its notes, on every new measurement. A standard model writes better notes.
    - **postdoc**: answers questions about the whole project, with its context, only when asked. It needs the strongest model; one run can cost more than a batch of notes.
  - The recommendations per tool are in `config/pipeline.yaml` → `agents.recommended`. `labpipe notes verify` and `labpipe postdoc verify` check that every number is found in the results, whatever the model; they do not check that it is used in the right place, so read the notes.
  - Write the answer into `config/local.yaml` → `agents`, then run `labpipe agents sync`.
- **Automatic processing** (optional, last): explain what it does: in the project's container, a watcher that checks for new files, waits until they stop changing, then runs the pipeline in batches of at most 10 measurements per AI run; a nightly safety-net run; notifications when work starts and ends and about anything new that needs the user (unrecognised files, decisions, failed and out-of-date analyses); the AI starts only when there is work. It needs container mode and starts with the container, which starts by itself at login (the installer asks). The user runs `labpipe automation setup` in their own terminal: it asks the timings, enables `podman-restart.service` (Podman on Linux, after a yes), shows `loginctl enable-linger $USER` for starting without logging in (never run it yourself), and removes the old native units if they exist. Doctor's `autostart` item says whether the container starts at login, `old_automation` warns about old native units (show the removal commands it gives, the user runs them), and `automation` reports whether the last run succeeded; if it warns, show the reason and the log. Without a container nothing runs by itself: `labpipe automation run`, or the user tells the agent "process the new data".

- **Project context** (optional, any time): for the postdoc (AGENTS.md → Project context and the postdoc). `labpipe context init`; the user puts the work plan and papers into `context/documents/`; `labpipe context index`; then write `context.md` together.
- **Uninstall** (when the user asks): show `~/.local/share/labpipe/app/uninstall.sh` (it lists what it removes and asks; `--dry-run` only shows; projects and data are never touched). The user runs it; never run it yourself.

Onboarding follows setup, when `labpipe doctor` is `ready` and shows the `onboarding` item: `docs/ONBOARDING.md`.

Keep a short record of the setup decisions (paths chosen, naming rule, standards) in the `note:` fields of the settings files you change, so the next person knows why.
